Audit apparatus / fault injection / source-preserving investigation

When 32 green lights miss a failing check

The official VMS symbolic-audit master can report “32 PASS” even when one of its own modules explicitly reports “FAIL.” A controlled mutation test demonstrates exactly how.

New / full-suite fault injection

31 module failures, 32 master passes

We extended the single-module negative control to every counter-based CAS module. Each of F0001–F0031 reported one injected failed check, but the unmodified master still reported 32 green blocks. The source-preserving systemic test includes a strict independent verdict, per-module results and a reproduction script.

Result / three controlled runs

The same runner, three different outcomes

We downloaded the institute's official SymPy audit ZIP and verified its SHA-256. Three tests used independent temporary extractions. The original archive was never edited. One run preserved the original code; a second deliberately corrupted a single expected result inside module F0001; a third deliberately raised an exception as a positive control.

Demonstrated defect: a failed inner check is not necessarily propagated into the top-level verdict. The master runner detects exceptions, but does not inspect the module's printed FAIL status or its internal fail_count.

Important limit

The unmodified source did not reveal a hidden failing F0001 step. Its 31 reporting modules reported 334 successful internal checks and zero failing internal checks. F0000 separately passed its 11 Python assertions. This experiment proves a weakness in the runner's failure detection, not that the original computational checks were already failing.

Cause / source inspection

Why the master can miss failure

The released sympy/run_master.py, lines 81–94, calls each module's run() inside a try block and records PASS if the call returns normally. The exception branch records FAIL. It does not examine printed subcheck counts. The 31 modules F0001–F0031 follow a pattern of incrementing fail_count and printing a verdict, without raising an exception or returning an explicit failure value at the end. F0000 is different: it contains 11 executable Python assertions.

In the mutation run, the expected value in F0001's Step 1 was changed from m × xdot to m × xdot + 1. Its symbolic comparison then reported one failed step. That local failure was visible in the module's output, but the master still marked its run as passing.

The positive-control run establishes the complementary behavior: an actual AssertionError is caught, F0001 is marked FAIL, and the master exits with code 1. Thus the fault is specifically in propagating reported check failures, not in handling Python exceptions.

Cross-block audit / skipped prerequisites

“Global consistency: PASS” also masks three skipped checks

The master runs constants.check_consistency() and constants.check_identities(). In the reproduced original run, the constant registry was empty; all three named cross-block identities were marked SKIP. The global boolean nevertheless remained true because the code accepts checks with absent prerequisites as successful overall.

Scope / no extrapolation

What the experiment does and does not establish

It demonstrates a reproducible audit-runner reliability defect. It does not demonstrate that all 32 original algebraic checks are false, that the institute's entire physical ontology is inconsistent, or that an external panel has accepted a prize-winning mathematical break.

Separately, the current symbolic audit ZIP does not explicitly implement the proposed Hodge-star transport current or source-balance equations in the institute's Mathematical Bridge source map. That is a coverage question. The present mutation experiment concerns failure propagation within code that does exist.

The full independent Mathematical Bridge challenge counterexample remains private pending determination of the published challenge terms. No contest submission or prize adjudication is claimed.

Engineering remediation / falsifiable retest

How the audit could be repaired

  1. Make every module expose a machine-readable, non-optional verdict, or raise an exception whenever fail_count > 0.
  2. Make the master reject a missing/unknown verdict rather than treating normal function return as proof of success.
  3. Require an explicit, nonempty expected registry of constants and show distinct PASS, FAIL and SKIP counts for every global check.
  4. Add fault-injection tests to continuous integration: each deliberately wrong subcheck must result in master failure and nonzero process exit.
  5. Publish a source-equation-to-test matrix, distinguishing checked identities, accepted premises, numerical calibrations and independent physical predictions.

The clean acceptance test is direct: repeat the same one-line fault injection. A repaired runner must report F0001 as failed at the top level and exit unsuccessfully, without needing the module to throw an exception.
